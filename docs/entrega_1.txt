Sobre el uso de inteligencia artificial
Puedes usar IA (ChatGPT, Claude, Copilot, v0…) para esta entrega. No está prohibido y no tiene sentido prohibirlo.
Pero esta entrega está diseñada para que pegar lo que diga la IA no alcance para una buena nota. La razón es simple: en la Entrega 2 vas a construir la API de este mismo proyecto, y todo lo que no entiendas ahora te va a costar entonces. Si no comprendes lo que entregaste, se te va a notar después.
Por eso la evaluación mira tres cosas que la IA no puede fingir por ti:
Tu historial de commits — cómo construiste el proyecto, paso a paso.
Tu README — si sabes explicar en tus palabras qué hiciste y por qué.
Retos que exigen decisiones tuyas — contenido real, reglas propias, lógica específica de tu dominio.
💡 La forma correcta de usar IA aquí es como un tutor: pregúntale por qué funciona algo, pídele que te explique un concepto, úsala para depurar. La forma que te va a costar la nota es pedirle "hazme un sitio web" y pegar el resultado.
1. Qué debes construir
Un sitio web (página de presentación) de un proyecto propio, hecha con HTML, CSS y JavaScript puro (sin frameworks: nada de React, Bootstrap ni Tailwind en esta entrega), publicada en Vercel y versionada en GitHub.
Este proyecto es el que vas a continuar toda la parte individual del curso:
Entrega 1 (sitio web, HTML/CSS/JS) → Actividad (nextjs, tailwind) → Entrega 2 (API REST del mismo dominio)
Así que elige un dominio que te sirva para las dos.
Cómo elegir tu dominio
Tú eliges el tema, pero debe cumplir estas reglas (son las que garantizan que sirva para la API después):
[ ] Tiene al menos dos tipos de cosas relacionables entre sí. Ejemplo: una biblioteca tiene libros y autores; una veterinaria tiene mascotas y dueños.
[ ] Una de esas cosas se puede mostrar como un catálogo o listado (varios elementos con foto, nombre, descripción, precio…).
[ ] Tiene sentido que alguien quiera registrarse o enviar un formulario (contacto, reserva, inscripción, pedido).
Ejemplos válidos: cafetería con menú, tienda de plantas, gimnasio con clases, academia de música con cursos, refugio de animales en adopción, portafolio de servicios freelance, agencia de viajes con destinos.
❌ No sirve: una página de una sola pantalla sin contenido repetible (ej. "página de mi banda" con solo un texto), porque no da para una API con recursos.
Cada estudiante debe tener un dominio distinto. Dos proyectos iguales (mismo tema y mismo contenido) se tratan como copia.
2. Requisitos técnicos
HTML — estructura y semántica
[ ] Estructura semántica real: <header>, <nav>, <main>, <section>, <footer> usados según su significado (no <div> para todo).
[ ] Un solo <h1> por página, jerarquía de encabezados coherente (h1 → h2 → h3).
[ ] HTML válido: sin etiquetas sin cerrar, sin atributos inventados. (Valídalo en https://validator.w3.org/)
CSS — diseño y responsive
[ ] Estilos en un archivo externo (styles.css), no <style> en el HTML ni estilos inline.
[ ] Layout con Flexbox y Grid — al menos uno de cada uno, cada uno donde tiene sentido.
[ ] El catálogo se muestra como una cuadrícula de tarjetas que cambia de columnas según el ancho.
JavaScript — interacción en el DOM
Mínimo tres interacciones distintas, y al menos una de cada grupo:
Grupo A — Manipulación del DOM
[ ] Menú de navegación que se abre/cierra en móvil (hamburguesa), o
[ ] Filtro del catálogo: botones que muestran/ocultan tarjetas por categoría, o
[ ] Contenido que se genera dinámicamente desde un arreglo de objetos en JS (no escrito a mano en el HTML).
Grupo B — Formularios y validación
[ ] Un formulario que valida con JavaScript antes de "enviar": campos requeridos, formato de email, longitud mínima. Los errores se muestran junto al campo, no en un alert.
Grupo C — Eventos
[ ] Al menos un addEventListener que responda a una acción del usuario (click, submit, input).
El catálogo generado dinámicamente desde un arreglo de objetos (Grupo A, tercera opción) es muy recomendable, porque en la Entrega 2 ese arreglo se reemplaza por los datos que vengan de tu API. Quien lo haga así tendrá medio camino andado.
Git — historial de trabajo
[ ] Repositorio público en GitHub.
[ ] Mínimo 6 commits con mensajes descriptivos que muestren avance progresivo. Ejemplos de buenos mensajes: estructura HTML del header, estilos responsive del catálogo, validación del formulario de contacto.
[ ] Los commits deben estar repartidos en el tiempo, no todos el mismo día a la misma hora. Un único commit gigante (primer commit con todo el proyecto) es señal de código pegado y baja la nota.
[ ] .gitignore apropiado (sin node_modules, sin archivos del sistema como .DS_Store).
Despliegue — Vercel
[ ] Sitio publicado en Vercel, accesible por una URL pública.
[ ] El despliegue está conectado al repositorio de GitHub: al hacer push a main, Vercel actualiza el sitio automáticamente.
[ ] La URL de Vercel está en el README y en la descripción del repositorio de GitHub.
README — tus decisiones explicadas
El README.md debe estar escrito en tus palabras (no generado por IA) y contener:
[ ] Descripción del proyecto: qué es, para quién, qué problema resuelve.
[ ] Link al sitio en Vercel.
[ ] Capturas de la página en móvil y escritorio.
[ ] Decisiones técnicas — responde estas preguntas en párrafos cortos:¿Dónde usaste Flexbox y dónde Grid, y por qué en cada caso?
¿Qué hace tu JavaScript, explicado sin copiar el código? ¿Cómo funciona tu validación?
Si usaste IA, ¿para qué la usaste y qué cambiaste tú del resultado?
¿Qué fue lo más difícil y cómo lo resolviste?
Esta sección de decisiones es la que separa una nota alta de una media. Un README genérico que podría servir para cualquier proyecto indica que no entendiste el tuyo.

Detalle por criterio
1. HTML semántico y válido · 15 pts 🟢 Etiquetas semánticas usadas correctamente, jerarquía de encabezados coherente, HTML válido en el validador. · 🟡 Usa algunas etiquetas semánticas pero abusa de <div>, o tiene errores de validación. · 🔴 Todo con <div>, sin estructura.
2. CSS: variables, Flexbox y Grid · 15 pts 🟢 CSS externo, variables usadas consistentemente, Flexbox y Grid cada uno donde corresponde. · 🟡 Usa CSS pero sin variables, o solo Flexbox, o mezcla estilos inline. · 🔴 Estilos inline o CSS mínimo sin estructura.
3. Responsive real · 15 pts 🟢 Se reorganiza bien en los tres tamaños, el catálogo cambia de columnas, nada se desborda. · 🟡 Responsive parcial: funciona en móvil y escritorio pero con problemas en algún punto. · 🔴 No es responsive o se rompe en móvil.
4. JavaScript: 3 interacciones · 20 pts 🟢 Tres interacciones distintas de los grupos A, B y C, funcionando y con código legible. · 🔵 Tres interacciones pero alguna con errores menores. · 🟡 Solo una o dos interacciones. · 🔴 Sin JavaScript funcional.
5. Formulario con validación propia · 10 pts 🟢 Valida requeridos, email y longitud; errores junto al campo; no envía si hay errores. · 🟡 Valida algo pero con alert, o solo campos requeridos. · 🔴 Formulario sin validación.
6. Git: historial progresivo · 10 pts 🟢 6+ commits repartidos en el tiempo, mensajes descriptivos que cuentan la construcción. · 🟡 Pocos commits o mensajes genéricos (cambios, update). · 🔴 Uno o dos commits con todo de golpe.
7. Despliegue en Vercel · 5 pts 🟢 Publicado, conectado a GitHub, se actualiza con push, URL en el README. · 🟡 Publicado pero subido manualmente, sin conexión a GitHub. · 🔴 No desplegado o la URL no carga.
8. README con decisiones · 10 pts 🟢 Descripción clara, capturas, y decisiones técnicas explicadas en palabras propias que demuestran entendimiento. · 🟡 README presente pero genérico, sin explicar decisiones. · 🔴 Sin README o solo el título.
